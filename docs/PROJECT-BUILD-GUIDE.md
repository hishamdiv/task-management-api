# دليل بناء ومشروع إدارة المهام السحابي (Project Build Guide)

هذا الملف هو دليلك الشامل لفهم المشروع بالكامل، تم إعداده بناءً على **الملفات والنتائج الحقيقية فقط** ليساعدك في مناقشة المشروع مع الدكتور بثقة تامة.

---

## 1. مقدمة بسيطة جدًا: ما هو مشروعنا؟
لدينا **Task Management REST API**، وهو باختصار نظام "إدارة مهام" يسمح للمستخدم بإنشاء مهمة جديدة، قراءتها، تعديلها، وحذفها. 
بدلاً من تشغيل هذا النظام بالطريقة التقليدية التي قد تفشل على أجهزة مختلفة، قمنا بتشغيله داخل **Containers (حاويات)** باستخدام **Docker**. 
استخدمنا **PostgreSQL** كقاعدة بيانات لتخزين هذه المهام، ووضعنا خادم **Nginx** ليكون نقطة الدخول الوحيدة (البوابة) أمام واجهة برمجة التطبيقات (API) لحمايتها وتنظيم الطلبات.

---

## 2. الصورة الكبيرة (System Architecture)
```text
المستخدم / Client
       |
       | HTTP Request (http://localhost:8080/api/tasks)
       v
Nginx :8080 (بوابة الدخول / Reverse Proxy)
       |
       | توجيه الطلب داخلياً
       v
Node.js + Express API :3000 (المنطق البرمجي)
       |
       | اتصال بقاعدة البيانات (DB Connection)
       v
PostgreSQL :5432 (قاعدة البيانات)
       |
       v
Docker Volume (task-management-db-data) (لحفظ البيانات بشكل دائم)
```
**الشرح من الأعلى للأسفل:**
العميل يرسل الطلب إلى المنفذ `8080` (الوحيد المفتوح للعالم). يستلم `Nginx` الطلب ويحوله سرّاً إلى الـ `API` العامل على المنفذ `3000` (المعزول داخلياً). يقوم الـ `API` بمعالجة الطلب، ويتواصل مع `PostgreSQL` على المنفذ `5432` لجلب أو حفظ البيانات. وتقوم قاعدة البيانات بكتابة البيانات في `Volume` لضمان عدم ضياعها.

## 3. مكونات المشروع

| المكون | ما هو؟ | وظيفته في مشروعنا |
| --- | --- | --- |
| **Node.js** | بيئة تشغيل للغة جافاسكربت | تشغيل كود الـ API الخاص بنا (الخلفية / Backend) |
| **Express** | إطار عمل (Framework) لـ Node.js | تسهيل إنشاء مسارات الـ API (Endpoints) مثل GET و POST |
| **PostgreSQL** | نظام إدارة قواعد بيانات علائقية | تخزين المهام (Tasks) بشكل مهيكل (جداول وصفوف) |
| **Docker** | منصة لإنشاء وتشغيل الحاويات | تغليف التطبيق وقاعدة البيانات ليعملوا في أي مكان بنفس الطريقة |
| **Docker Image** | قالب ثابت (وصفة) | يحتوي على كود التطبيق ونظام التشغيل المصغر (Alpine) الجاهز للتشغيل |
| **Docker Container** | بيئة تشغيل حية (نسخة شغالة) | التشغيل الفعلي للـ Image في الذاكرة (لدينا 3 حاويات: api, db, nginx) |
| **Docker Compose** | أداة لتشغيل عدة حاويات معاً | يقرأ `compose.yaml` ويشغل كل حاويات المشروع ويربطها بشبكة واحدة بضغطة زر |
| **Nginx** | خادم ويب ووكيل عكسي (Reverse Proxy) | يستقبل طلبات المستخدم ويوجهها للـ API، ويعزل الـ API عن العالم الخارجي |
| **Docker Hub** | مستودع سحابي للصور (Registry) | رفع صورة الـ API الخاصة بنا `hishamdiv/task-management-api` ليتمكن أي شخص من تحميلها |
| **Git** | نظام تحكم بالإصدارات | تتبع التغييرات في ملفات الأكواد وحفظ تاريخ التطوير |
| **GitHub** | منصة سحابية لاستضافة Git | حفظ الكود المصدري للمشروع كمرجع ونسخة احتياطية ولمشاركته |

## 5. كيف بدأ بناء المشروع؟ (مراحل البناء الحقيقية)

1. **المرحلة الأولى:** قمنا بكتابة الـ REST API باستخدام Node/Express وربطه بـ PostgreSQL.
2. **المرحلة الثانية:** كتبنا `Dockerfile` لإنشاء صورة (Image) خاصة بتطبيقنا.
3. **المرحلة الثالثة:** أضفنا `Nginx` كوكيل عكسي بكتابة ملف `nginx.conf`.
4. **المرحلة الرابعة:** أنشأنا `compose.yaml` لتشغيل `api`, `database`, `nginx` معاً وتفعيل الـ Volume للحفظ.
5. **المرحلة الخامسة:** أنشأنا حسابات Git ورفعنا الكود لـ GitHub.
6. **المرحلة السادسة:** اختبرنا الفشل (ماذا لو توقف API أو DB) ونفذنا السكربتات.
7. **المرحلة السابعة:** جمعنا الأدلة (Evidence) وهذا الدليل لتوثيق كل شيء.

## 6. Dockerfile بالتفصيل

```dockerfile
FROM node:24-alpine
WORKDIR /usr/src/app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
USER node
EXPOSE 3000
CMD ["npm", "start"]
```
*   `FROM node:24-alpine`: نبدأ من نسخة خفيفة جداً من نظام Linux (Alpine) مجهزة بـ Node.js 24.
*   `WORKDIR /usr/src/app`: تحديد المجلد الافتراضي داخل الحاوية.
*   `COPY package*.json ./`: نسخ ملفات التعريف بالحزم أولاً.
*   `RUN npm install --omit=dev`: تثبيت الحزم المطلوبة للتشغيل فقط (بدون أدوات التطوير) لتقليل الحجم.
*   `COPY . .`: نسخ باقي الكود المصدري (مثل `index.js`).
*   `USER node`: أوامر أمنية لتشغيل التطبيق كمستخدم عادي وليس كـ Root.
*   `EXPOSE 3000`: إعلام Docker بأن التطبيق يعمل على منفذ 3000 داخلياً.
*   `CMD ["npm", "start"]`: الأمر الذي سيعمل عند تشغيل الحاوية.

**لماذا الترتيب مهم؟ (Layer Caching):**
لأننا نسخنا `package.json` ونفذنا `npm install` قبل نسخ الكود (`COPY . .`). إذا عدّلنا كود التطبيق فقط، لن يقوم Docker بإعادة تثبيت الحزم (التي تستغرق وقتاً)، بل سيستخدم الـ Cache (الذاكرة المخبأة).

## 7. كيف يتم بناء Image؟
الأمر: `docker build -t task-api:v1.0.0 .`
*   `docker build`: أمر البناء.
*   `-t task-api:v1.0.0`: إعطاء اسم للصورة (`task-api`) ونسخة (`v1.0.0`).
*   `.`: يعني اقرأ ملف Dockerfile من المجلد الحالي.
**النتيجة:** يقوم Docker بقراءة التعليمات سطرًا سطرًا ويصنع `Docker Image` جاهزة.

---

## 8. Image vs Container
*   **Image (الصورة):** هي الوصفة أو "الأسطوانة" التي تحتوي على البرنامج. لا تستهلك معالج (CPU) ولا تعمل بمفردها. (مثالنا: `task-api:v1.0.0`).
*   **Container (الحاوية):** هي "البرنامج وهو يعمل". عندما نشغل الصورة، تصبح حاوية. يمكن تشغيل 10 حاويات من صورة واحدة.

---

## 9. Docker Compose
ملف `compose.yaml` الخاص بنا يحتوي على 3 خدمات:
*   **database:** تستخدم صورة `postgres:15-alpine`، تحتوي على كلمة مرور واسم المستخدم (متغيرات بيئة)، ومربوطة بـ Volume لحفظ البيانات، ولديها `healthcheck` لتخبرنا متى تصبح جاهزة.
*   **api:** تُبنى من المجلد المحلي `./api`، تعتمد على قاعدة البيانات (`depends_on: database` بشرط `service_healthy`) لكي لا تبدأ قبل أن تجهز القاعدة. تتصل بالقاعدة عبر متغيرات البيئة.
*   **nginx:** تستخدم صورة `nginx:alpine`، تفتح المنفذ الخارجي `8080` وتربطه بالمنفذ الداخلي `80`.

---

## 10. Docker Network
*   **ما هي؟** شبكة افتراضية اسمها `task-management-network` أنشأها Compose لربط الحاويات معاً.
*   **كيف تتواصل؟** عبر أسمائها! الـ API يتصل بالقاعدة باستخدام الاسم `database` وليس `localhost`.
*   لماذا ليس `localhost`؟ لأن `localhost` داخل حاوية API يعني "داخل حاوية الـ API نفسها"، بينما القاعدة تعيش في حاوية أخرى.

---

## 11. Nginx Reverse Proxy
في ملف `nginx.conf` كتبنا:
```nginx
upstream backend {
    server task-management-api:3000;
}
```
*   **ما هو؟** Nginx يعمل كـ "وكيل عكسي" (بوابة الاستقبال).
*   **وظيفته:** يستلم الطلب من المستخدم على `8080`، ويرسله داخلياً إلى `task-management-api:3000`.
*   **لماذا لم نكشف API؟** لعزل الـ API أمنياً، وللسماح لاحقاً بوجود أكثر من API خلف Nginx (Load Balancing) إن أردنا توسيع المشروع.

---

## 12. REST API (Node + Express)
*   التطبيق مبرمج بـ Node.js ويستخدم إطار Express لتسهيل استقبال الطلبات.
*   يتصل بالقاعدة باستخدام مكتبة `pg` (PostgreSQL Client).
*   **الـ Endpoints الفعلية الموجودة:**
    *   `GET /api/tasks` (قراءة المهام)
    *   `POST /api/tasks` (إنشاء مهمة)
    *   `PUT /api/tasks/:id` (تحديث مهمة)
    *   `DELETE /api/tasks/:id` (حذف مهمة)
    *   `GET /api/tasks/:id` (قراءة مهمة واحدة)

---

## 13. Request Lifecycle (حياة الطلب)
ماذا يحدث عند طلب `GET http://localhost:8080/api/tasks`؟
1. **Client**: يرسل الطلب عبر المتصفح/Postman إلى المنفذ 8080.
2. **Nginx**: يستقبل الطلب، يقرأ الإعدادات، يكتشف أنه يجب توجيهه إلى `task-management-api:3000`.
3. **API**: يستلم الطلب في Express، يقوم بتنفيذ أمر SQL (`SELECT * FROM tasks`).
4. **PostgreSQL**: ينفذ الاستعلام، ويقرأ البيانات من القرص (Volume)، ويعيدها للـ API.
5. **API**: يحول البيانات إلى صيغة `JSON` ويرسلها لـ Nginx.
6. **Nginx**: يرسل الـ JSON النهائي للعميل.

---

## 14. PostgreSQL (قاعدة البيانات)
*   **Database**: اسمها الفعلي لدينا هو `taskdb`.
*   يتم تخزين المهام في جداول. المهمة تتكون من أعمدة: `id` (Primary Key), `title`, `description`, `status`.

---

## 15. Docker Volume و Persistence (الاستمرارية)
*   **Container Storage:** لو حفظنا البيانات داخل الحاوية مباشرة، فبمجرد حذف الحاوية تطير البيانات.
*   **Docker Volume:** قرص تخزين منفصل يديره Docker. في مشروعنا اسمه `task-management-db-data` مربوط بـ `/var/lib/postgresql/data` داخل الحاوية.
*   **كيف أثبتناه؟** أنشأنا مهمة (Task)، أوقفنا الحاوية `docker compose stop task-management-db`، ثم أعدنا تشغيلها، ووجدنا أن البيانات ما زالت موجودة.

---

## 16. Security (الأمان)
إجراءات الأمان المطبقة فعلياً في المشروع:
1. **API/DB Isolation**: الـ API وقاعدة البيانات غير مكشوفين للخارج إطلاقاً (لا يوجد Ports في Compose لهم، فقط شبكة داخلية). يمنع الاختراق المباشر.
2. **Nginx Entry Point**: بوابة واحدة محكومة.
3. **USER node**: تشغيل الكود بصلاحيات مستخدم عادي (ليس root) لمنع سيطرة المخترق على الحاوية بالكامل.
4. **.gitignore**: منع رفع ملفات الحزم الثقيلة أو أي أسرار عن طريق الخطأ لـ GitHub.

## 17. Docker Hub (مستودع الصور)
العملية:
* قمنا ببناء الصورة.
* أضفنا لها وسماً (Tag): `docker tag task-api:v1.0.0 hishamdiv/task-management-api:latest`.
* سجلنا الدخول بحسابك `docker login`.
* رفعنا الصورة `docker push`.
* **v1.0.0**: نسخة ثابتة (رقم الإصدار الأول).
* **latest**: وسم ديناميكي يشير لآخر نسخة تم رفعها.
* **Digest**: هو بصمة فريدة للصورة. الـ Digest لمشروعنا هو `sha256:799e625d06f9fdacb5a12da1edc08556a029c7c809e3ec2b238005803cba694d`. تم التحقق من نجاح الرفع بإعادة سحبها `docker pull` وحذفها محلياً أولاً لإثبات السحب النظيف (Clean Pull).

## 18. Git و GitHub
*   **Repository**: المستودع الذي يحوي الكود.
*   **Branch**: مسار العمل (نحن نستخدم `main`).
*   **Commit**: أخذ لقطة حفظ (Save) للكود مع رسالة تصف ما تم تعديله.
*   قمنا فعلياً بعمل عدة `Commits` (مثل "feat: initial project setup" و "docs: document Docker Hub").
*   قمنا برفع الكود `git push` إلى مستودعك `task-management-api` ليصبح متاحاً على الإنترنت للحفظ والمشاركة.

## 19. Testing (الاختبار)
أنشأنا ملف `api/tests/test.js`:
*   **ماذا يختبر؟** يرسل طلب `GET /api/tasks` إلى `localhost:8080`.
*   **كيف يعمل؟** عبر `node api/tests/test.js`.
*   **النتيجة؟** يتحقق من أن حالة الرد هي `200 OK` ويطبع محتوى الاستجابة. (نجح الاختبار فعلياً).
*   **ما لم يختبره هذا الملف برمجياً؟** (POST, DELETE, PUT) تم اختبارها يدوياً (Manual Runtime Testing) عبر `curl.exe`، لكن السكربت يختبر الـ GET فقط.

## 20. Failure Modes (سيناريوهات الفشل الفعلية التي جربناها)
1. **API stopped**: أوقفنا الـ API. عندما دخلنا عبر Nginx ظهر لنا `502 Bad Gateway` لأن Nginx لم يجد السيرفر الخلفي.
2. **Database stopped**: أوقفنا الـ DB. عندما طلبنا المهام من API ظهر `500 Internal Server Error` لأن الـ API عجز عن جلب البيانات.
3. **Nginx stopped**: فشل الاتصال تماماً `Connection Refused` لأن البوابة مغلقة.
4. **Invalid API Request**: أرسلنا طلب لـ ID غير موجود فعاد لنا `404 Not found` (مبرمج في الـ API).

---

## 21. ماذا يحدث عند تشغيل `docker compose up -d`؟
1. ينشئ الشبكة `task-management-network`.
2. ينشئ/يربط الـ Volume `task-management-db-data`.
3. يشغل `database` وينتظرها حتى تصبح `Healthy` (عبر الـ healthcheck).
4. بعد أن تجهز، يشغل `api`.
5. يشغل `nginx` ويربط المنافذ.
*حرف `d` يعني تشغيلها في الخلفية (Detached).*

---

## 22. ماذا يحدث عند إيقاف `docker compose down`؟
يوقف جميع الحاويات ويحذفها هي والشبكات. **ولكنه لا يحذف Volumes**.
*   **تحذير**: لو استخدمنا `docker compose down -v`، سيحذف الـ Volumes وتطير كل البيانات في PostgreSQL!

## 24. أسئلة الدكتور المحتملة (30 سؤال وجواب من المشروع الحقيقي)

### أسئلة أساسية
1. **ما هو Docker؟** أداة لتشغيل التطبيقات داخل بيئات معزولة تسمى حاويات.
2. **ما هو Container؟** بيئة تشغيل معزولة تحتوي على كل ما يحتاجه التطبيق ليعمل.
3. **ما هو Image؟** قالب غير قابل للتعديل يُبنى منه الحاوية.
4. **ما الفرق بين VM و Container؟** الـ VM يقلد الهاردوير ويحتاج نظام تشغيل كامل، الـ Container يشارك نواة نظام التشغيل (Host OS) لذلك هو أسرع وأخف بكثير (استخدمنا Alpine).

### أسئلة Architecture
5. **لماذا استخدمتم Nginx؟** ليكون بوابة أمامية (Reverse Proxy) تستقبل الطلبات وتحمي الـ API.
6. **لماذا لم نفتح منفذ API مباشرة؟** لعزله أمنياً، ليكون الوصول له فقط عبر Nginx.
7. **كيف يتم ترتيب التشغيل؟** استخدمنا `depends_on` في Compose لضمان بدء القاعدة أولاً.

### أسئلة Database & Storage
8. **كيف حفظتم البيانات من الضياع؟** باستخدام Docker Volumes (تحديداً `task-management-db-data`).
9. **ما اسم قاعدة البيانات المستخدمة؟** PostgreSQL (اسم القاعدة `taskdb`).
10. **أين تُحفظ البيانات داخل الحاوية؟** في المسار `/var/lib/postgresql/data`.

### أسئلة Networking
11. **كيف يتواصل API مع Database؟** عبر شبكة Docker الداخلية واسم الحاوية (`database`).
12. **لماذا لا نستخدم `localhost` لربط الحاويات؟** لأن `localhost` يعود للحاوية نفسها وليس للحاويات الأخرى.
13. **ما هو المنفذ الخارجي للمشروع؟** 8080.
14. **ما هي الشبكة المستخدمة في المشروع؟** شبكة من نوع `bridge` اسمها `task-management-network`.

### أسئلة Security
15. **لماذا أضفتم `USER node` في Dockerfile؟** لعدم تشغيل الكود بصلاحيات الرووت (Root) كإجراء أمني (Least Privilege).
16. **ما فائدة `.gitignore` هنا؟** منع رفع ملفات `node_modules` الثقيلة أو أي ملفات بيئة `.env` سرية.
17. **هل هناك أسرار في GitHub حالياً؟** لا، تم التحقق من ذلك ولا يوجد `.env` في تاريخ الـ Commits.
18. **هل يمكن لشخص خارجي الوصول للـ DB؟** لا، لأننا لم نقم بعمل Port mapping لها.

### أسئلة Testing & Failure
19. **ماذا يحدث لو توقف الـ API؟** يقوم Nginx بإرجاع خطأ 502 (بوابة سيئة).
20. **ماذا يحدث لو توقفت قاعدة البيانات؟** يقوم API بإرجاع خطأ 500 (خطأ داخلي في الخادم).
21. **كيف أثبتم الـ Persistence؟** أنشأنا بيانات، أوقفنا حاوية DB، شغلناها مجدداً، وكانت البيانات موجودة.
22. **هل لديكم Automated Test؟** نعم، سكربت `test.js` يفحص مسار `GET /api/tasks`.

### أسئلة Dockerfile & Image
23. **لماذا استخدمتم نسخة Alpine؟** لأنها صغيرة جداً وخفيفة مما يسرع التحميل ويقلل الثغرات.
24. **لماذا `COPY package.json` قبل نسخ باقي الكود؟** للاستفادة من ذاكرة التخزين المؤقت (Layer Caching) في Docker ولتسريع عملية البناء اللاحقة.
25. **ما معنى `--omit=dev`؟** عدم تنزيل حزم المطورين، فقط الحزم الضرورية للتشغيل.

### أسئلة Registry & Git
26. **أين استضفتم الـ Image؟** في Docker Hub على مسار `hishamdiv/task-management-api`.
27. **ما الفرق بين v1.0.0 و latest؟** `v1.0.0` هو إصدار ثابت محدد، `latest` هو مؤشر لآخر إصدار تم رفعه.
28. **كيف تأكدتم أن الـ Image رُفعت بشكل سليم؟** حذفناها من جهازنا (Local) وقمنا بعمل `docker pull` من السيرفر.
29. **ما هو الـ Digest؟** بصمة فريدة لا تتغير (Hash) تثبت سلامة ومحتوى الصورة.
30. **ما هي منصة Git المستخدمة وما دورها؟** GitHub لحفظ الكود المصدري للمشروع.

## 25. كيف أشرح المشروع للدكتور في 60 ثانية؟
"مشروعنا هو عبارة عن واجهة برمجة تطبيقات (REST API) لإدارة المهام مبنية بـ Node.js و Express. قمنا بتحويل هذا التطبيق ليعمل داخل حاويات (Containerization) باستخدام Docker، مما يحل مشكلة اختلاف بيئات التشغيل.
المعمارية تتكون من 3 حاويات: حاوية لقاعدة بيانات PostgreSQL، حاوية للـ API، وحاوية لـ Nginx تعمل كوكيل عكسي (Reverse Proxy) ليكون نقطة الدخول الوحيدة بأمان.
استخدمنا Docker Compose لربطهم وتحديد أولوية التشغيل، واستخدمنا Docker Volumes لضمان عدم ضياع المهام عند إيقاف النظام. وأخيراً، قمنا برفع صورة التطبيق (Image) على Docker Hub لتسهيل النشر، وحفظنا الكود في GitHub."

## 26. كيف أشرح المشروع في 5 دقائق؟
1. **الفكرة**: نظام Task Management يوفر عمليات CRUD.
2. **التقنيات**: Node.js للبرمجة، Postgres للبيانات، Docker للحاويات.
3. **التصميم (Architecture)**: عزلنا الـ API والـ DB في شبكة داخلية. العميل يتواصل فقط مع Nginx على منفذ 8080.
4. **الـ Dockerfile**: استخدمنا نسخة Alpine الخفيفة، ورتبنا الطبقات (Layers) للاستفادة من الكاش، وعينا `USER node` للحماية.
5. **الاستمرارية (Persistence)**: لتجنب ضياع البيانات برمجنا Named Volume اسمه `task-management-db-data`.
6. **الاختبار والانهيار (Failure Modes)**: جربنا إيقاف الـ API وحصلنا على 502 من Nginx، وجربنا إيقاف الـ DB وحصلنا على 500، مما يثبت صحة الترابط ومعالجة الأخطاء.
7. **الختام**: الكود محفوظ أمنياً في GitHub، والصورة جاهزة للسحب من Docker Hub باستخدام الـ Tags `v1.0.0` و `latest`.
